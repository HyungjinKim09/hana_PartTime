# 개인별 로그인과 공용 자료의 작업자 기록

상태: 설계 검토 대기. 제품 코드·DB·운영 계정은 아직 변경하지 않았다.

## 목적과 확인된 요구

현재 공용 계정으로 작업하여 누가 사진을 올리거나 기록을 수정했는지 구분할 수 없다. 사용자는 **개인별 로그인 + 공용 자료 유지**를 선택했다. 계정은 개인별로 구분하되 팀의 기존 사진·일정·주소 폴더·도면을 계속 함께 보고 작업할 수 있어야 한다.

기존 자료에는 작성자 정보가 없다. 과거 작업자를 추정해서 붙이지 않고 `기존 자료 · 작업자 기록 없음`으로 표시한다. 계정과 작업자 기록은 구현 후의 작업부터 정확하게 연결한다.

## 동작

1. 기존 공용 계정은 초기 관리자 계정으로 유지한다. 관리자가 팀원의 로그인 아이디, 표시 이름, 비밀번호를 등록한다. 공개 회원가입이나 이메일 인증은 추가하지 않는다.
2. 팀원은 자신의 아이디·비밀번호로 로그인한다. 같은 사진과 폴더를 보고 기존과 같이 조사 작업을 할 수 있다. 화면에 현재 로그인한 사람의 이름을 표시한다.
3. 사진에는 업로드한 사람과 저장 시간을 표시한다. 일정에는 등록자와 최근 수정자를, 조사 상태·비고와 도면에는 최근 수정자를 표시한다.
4. 폴더의 작업 이력에서 누가 언제 사진 등록·삭제, 일정 등록·수정·삭제, 조사 기록 수정, 도면 저장을 했는지 확인한다. 삭제된 대상의 이력은 남긴다. 전체 작업 이력은 작업자와 작업 종류로 검색하고 페이지를 나눠 조회한다.
5. 관리자만 개인 계정을 추가하고 비밀번호 재설정·사용 중지·재활성화를 한다. 비밀번호는 조회하거나 다시 표시하지 않는다. 중지하거나 비밀번호를 변경한 계정의 기존 로그인은 즉시 무효화한다.
6. 기존 공용 로그인 정보가 알려진 팀원은 관리자 계정으로도 들어갈 수 있으므로, 실제 개인 계정 전환 시 관리자가 기존 관리자 비밀번호를 변경한다. 개인 계정만으로 로그인한 작업은 해당 계정에 연결하며, 관리자 계정에서 한 작업은 `관리자`로 기록한다.

## 계정과 자료의 연결

- 기존 `owner`는 공용 자료의 소유 범위다. 개인 계정 ID를 `owner` 대신 쓰지 않는다. R2 경로와 기존 일정·사진 ID를 옮기거나 복사하지 않는다.
- 개인 계정에는 불변 ID, 공용 owner, 로그인 아이디, 표시 이름, 비밀번호 해시·salt, 활성 상태, 인증 버전을 저장한다. 기존 PBKDF2 해시 방식과 로그인 시도 제한을 유지한다.
- 세션과 refresh 세션에는 개인 계정 ID·인증 버전을 연결한다. API마다 공용 owner와 작업자 ID를 검증된 세션에서 얻는다. 클라이언트가 보낸 작업자 이름·ID를 기록의 근거로 받지 않는다.
- 개인 계정의 표시 이름을 바꿔도 과거 기록의 이름은 유지하도록 작업 당시의 이름을 함께 저장한다. 계정 사용 중지는 자료나 과거 이력을 삭제하지 않는다.
- 기존 15분 access·90일 refresh 쿠키, 동시 탭 갱신, 로그아웃 폐기 동작을 유지한다. 사용 중지·비밀번호 변경 후에는 refresh도 거부한다.
- 전환 이전 공용 세션으로 개인 작업자를 식별할 수 없으므로 운영 전환 시 기존 세션을 종료하고 다시 로그인하게 한다. 자료 자체에는 영향을 주지 않는다.
- 팀원은 기존 자료 작업 권한을 유지한다. 계정 관리·계정 복구·저장 한도 설정은 관리자로 제한하고 기존 관리자 키 확인을 유지한다.

## 기록과 저장의 일관성

- 사진·일정·도면의 작성자/수정자 메타데이터와 별도의 작업 이력을 D1에 저장한다. 이력에는 작업자 ID·당시 이름, 대상 종류·ID·폴더 범위, 작업 종류, 서버 시간을 기록한다. 비밀번호·토큰·전체 연락처·비고 본문은 이력에 복제하지 않는다.
- 자료 저장과 이력 등록은 같은 D1 트랜잭션에서 처리한다. 저장에 실패하거나 revision 충돌이 발생하면 성공 이력을 남기지 않는다. 업로드 요청이 재전송되어도 기존 업로드 작업 번호에 대해 사진·이력을 중복 생성하거나 최초 업로더를 바꾸지 않는다.
- 폴더 삭제를 시작할 때 대상을 잠그는 기존 절차와 함께 삭제 시작 이력을 남긴다. 작업자는 삭제를 시작한 사람으로 고정한다. 중단 후 재시도는 별도 중복 삭제로 표시하지 않으며, 완료 여부를 함께 기록한다. 여러 파일을 지우는 요청은 폴더/일괄 작업 단위로 표시한다.
- 복원 시 원본 백업의 작성자 표시 정보는 보존하고, 복원 실행자는 별도 복원 작업으로 남긴다. 계정의 비밀번호·세션은 자료 백업에 포함하지 않는다. 이전 형식의 백업은 작성자 미확인으로 복원할 수 있다.
- 미전송 사진은 개인 계정별로 기기 임시 보관 범위를 구분한다. 이전 공용 계정의 미전송 보관함은 관리자에서 계속 복구할 수 있게 유지한다.

## 성능과 화면

- 기존 지역·날짜·주소 목록 요약 API와 5분 위치 캐시를 유지한다. 모든 기록이나 계정 목록을 `library` 응답에 실어 보내지 않는다.
- 현재 일정·사진 페이지에 필요한 이름만 메타데이터로 포함한다. 상세 이력은 사용자가 열 때 별도 조회하며 기본 50건·최대 100건, 다음 페이지를 제공한다.
- 사진은 기존 원본을 그대로 저장한다. 작업자 구분을 위해 사진 복제나 썸네일 생성, 외부 인증 서비스 도입을 하지 않는다.
- 모바일은 촬영과 정보 확인을 우선한다. 작업자 표시는 사진 설명과 조사 기록에 짧게 넣고, 상세 이력은 별도 버튼으로 연다. 관리자 메뉴는 일반 팀원에게 표시하지 않는다.

## 적용할 코드 범위

- D1 마이그레이션·`db/schema.ts`: 개인 계정, 세션의 계정 연결, 작성자/수정자, 작업 이력과 조회 인덱스.
- `lib/site-auth.ts`, `lib/session-lookup.ts`, `lib/refresh-sessions.ts`, `lib/storage.ts`, `cloudflare/worker.ts`: 개인 로그인, 요청별 작업자 조회, refresh/로그아웃/중지 검증.
- `app/api/session`, `app/api/account` 및 개인 계정 관리 API: 기존 관리자 연결, 관리자 전용 계정 등록·수정.
- 사진, 일정, 폴더 조사 기록, 삭제, 도면, 백업·복원 API: 서버 작업자 정보와 원자적 이력 기록.
- 로그인·계정 관리·보관함·사진 설명·조사 기록 화면, 관련 타입과 미전송 사진 범위.
- 이력 조회 API와 화면: 공용 owner 범위, 작업자/종류 필터, 페이지 제한.

## 검증 기준

- 서로 다른 개인 계정 A/B가 같은 기존 폴더·사진을 조회한다. 별도 owner로 자료가 갈라지지 않는다.
- A의 사진 업로드, B의 일정·비고·도면 수정이 각각 올바른 사람으로 표시된다. 클라이언트의 가짜 작업자 필드는 영향을 주지 않는다.
- 저장 실패·충돌·중복 업로드·삭제 재시도에서 거짓 성공이나 중복 이력이 생기지 않는다.
- 팀원이 계정 관리 API를 호출하면 거부한다. 사용 중지·비밀번호 재설정 뒤에는 access와 refresh를 모두 거부하며 다른 팀원은 계속 로그인할 수 있다.
- 자동 로그인, 동시 탭, ZIP 원본 다운로드, 로그아웃과 자료 접근 보호의 기존 검사를 유지한다.
- 기존 자료와 구형 백업은 작성자 미확인으로 표시하고, 새 형식 백업은 작성자 표시와 복원 실행자 이력을 검증한다.
- 목록 응답의 범위 제한, 캐시 재사용, 이력 페이지 경계와 모바일 화면을 확인한다.

## 실행 범위

설계 승인 후 로컬 테스트 DB와 합성 팀원 계정으로 구현·검증한다. 운영 데이터·계정·마이그레이션, Git 업로드, 배포는 이후 사용자의 배포 요청에 맞춰 진행한다. 작업자 이름이나 실제 비밀번호를 이 대화로 전달할 필요는 없다. 관리자가 완성된 계정 관리 화면에서 입력할 수 있어야 한다.
